# Cross-Tab Early Warning and Home Layout

Status: Implemented / focused checks pass / Human Browser Acceptance pending

## Contract and implementation

The Home screen reports loss-sensitive work in another live NarrativeLine tab before the user starts a Dataset acquisition. The notice is informational; it does not replace the existing guarded replacement or stale-writer checks. It explains that work should be applied or canceled in its source tab and that a changed Dataset may need to be exported before retrying.

A clean peer tab does not produce a strong warning. When the app cannot verify peer state, Home says verification failed and does not claim that unsaved work exists. Same-app status changes are observed through the app-specific localStorage marker and Web Locks namespace. Other E2R applications' lock names are ignored.

Home spans the available app-content width. Its content group keeps the 22rem reading width and is centered within that region. The inline notice wraps text without narrowing Timeline or forms. The existing Timeline work warning remains unchanged.

## Human Browser finding and follow-up

Human Browser Review found that a fresh single-tab InPrivate launch could keep the uncertainty notice visible until the window received focus. Code review found that Home queried peer status before this tab's Web Lock registration completed, and that an unknown result had no automatic retry. Those gaps explain why a transient initial failure could persist until focus. The exact browser condition that caused the original first query to be unavailable was not established. The notice was not changed to treat unknown as clean.

Peer status now waits for this tab's registration before querying. While Home is visible, an unknown result is retried after 1.5 seconds; retries stop once the status is known. Focus, pageshow, and same-app storage changes still trigger immediate refreshes. A request-generation check ignores stale responses. If coordination remains unavailable, the uncertainty notice remains visible. Replacement safety and fail-closed writes are unchanged.

## Follow-up: Home replacement-refusal layout — 2026-10-10

Home's vertical centering was intact. The remaining Human finding was a layout failure: B's refusal reason and Retry / Cancel actions appeared detached at the left immediately above the footer.

The refusal UI was rendered as a sibling of `HomeScreen` in `AppFrame`'s `.app-content`, while Home's own content group centers at a constrained reading width. Consequently, the refusal section did not share the Home content's centered width and visual context. The refusal section is now passed into `HomeScreen` and rendered inside `.home-screen-content`, alongside the early warning and acquisition feedback. Its text can wrap, its width is bounded by the existing Home content width, and the actions stay with the explanation. The replacement confirmation dialog and non-Home feedback retain their existing placement. Retry, Cancel, reload, and replacement checks are unchanged; this is a presentation correction only.

## Follow-up: Home feedback consolidation and cancel recovery — 2026-10-10

Human Browser Review retained PASS for the bounded two-tab safety path: the unapplied title is surfaced, replacement is refused, and a safe retry succeeds once the work is resolved. It identified two remaining Home UX failures: the peer-work warning duplicated the same explanation shown with a refused candidate's Retry / Cancel actions, and after Cancel the peer-work explanation could appear detached near the footer. The peer warning must remain while the peer still has work; only the candidate-specific feedback should disappear on Cancel.

The refusal result already distinguishes `blockedByPeer` from a saved-revision conflict. Home had not used that result distinction to choose its message priority, so the early peer warning and the candidate refusal were both rendered. The refusal path is now tracked explicitly. When a candidate is refused because another live tab has work, Home temporarily presents the refusal reason with its recovery actions and suppresses the duplicate early warning. Cancel clears candidate-specific state and refreshes peer status. If the follow-up shared-workspace save is also denied by the same peer, Home uses the early warning as the single explanation rather than leaving a second generic alert. The app records the `blockedByPeer` result as evidence of active peer work so this warning is not lost between the refusal and the asynchronous status refresh. Starting another acquisition clears prior refusal state. Other failure types, including stale-revision and unverifiable safety failures, retain their distinct feedback.

Home's replacement refusal and other Home-level safety errors are rendered within `.home-screen-content`; the replacement dialog remains a modal and Timeline feedback keeps its existing screen placement. This keeps the explanation and actions within the established reading width, preserves Home centering, and leaves the actual replacement guard unchanged. The modal decision, replacement candidate, storage comparison, export path, and fail-closed behavior are not weakened.

Automated regression coverage now checks that a peer-blocked candidate shows one explanation with Retry / Cancel, that the saved Dataset stays unchanged, that Cancel removes candidate UI while restoring the still-active peer warning inside Home, and that the candidate can still be retried after peer work clears. This known runner issue remains unresolved and is not counted as a pass.
