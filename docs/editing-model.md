# NarrativeLine Editing Model

## Purpose

This document describes how NarrativeLine edits E2R datasets.

It defines the behavior of dataset modification independently from the user interface.

Visual presentation and interaction design are described separately in `ui-spec.md`.

---

# Design Principles

NarrativeLine follows these principles:

- Modify as little data as possible.
- Preserve existing datasets whenever possible.
- Edit only information the application understands.
- Generate derived structures automatically whenever practical.
- Keep the E2R Dataset internally consistent.

---

# Dataset Creation

NarrativeLine creates a new Dataset with:

- the top-level Core `version` set to `1.0`
- a UUID v7 `extensions.metadata.datasetId`
- empty Event, Entity, and Relation collections

The Dataset ID remains stable during ordinary editing. Creating another Dataset
generates another Dataset ID. The onboarding sample has its own fixed Dataset
ID.

A newly created empty Dataset uses the Metadata Extension because it has a
Dataset ID. It does not use the History Extension merely because NarrativeLine
supports History editing, and it does not add a common Extension version
wrapper.

The optional `extensions.metadata.title` field is omitted until a user assigns
a Dataset title. A displayed placeholder is not stored as a title.

An imported Dataset may omit `extensions.metadata` or `datasetId`. Opening or
importing such a Dataset does not by itself assign an identity. Existing
Dataset IDs and unknown Dataset-level Extension data are preserved whenever
practical.

---

# Editing Unit

The primary editing unit is an Event.

Users edit Events directly.

Entities and Relations are updated automatically when required.

---

# Event Creation

Creating an Event performs the following operations:

1. Create a new Event.
2. Assign a unique identifier.
3. Insert the Event into the dataset.
4. Recalculate timeline ordering if necessary.

No Entity association is required.

The newly created Event is an application-level draft until the user saves it
or uses Save and Add Related Entity. Canceling Event Detail while it is a draft
removes the Event and any Relations created for it. This draft status is not
stored in the E2R Dataset.

---

# Event Modification

Users may edit:

- name
- description
- temporal information

Event Detail keeps changes locally until the user saves or uses Save and Add
Entity. Cancel discards only the local unsaved changes.

When saving an imported Event, NarrativeLine updates only fields whose editor
values differ from their initial values. Optional fields omitted by the imported
Dataset therefore remain omitted unless the user edits them.

For an existing Event, Cancel does not remove the Event. For a newly created
draft Event, Cancel removes the draft as described in Event Creation.

Timeline ordering is updated automatically whenever a saved temporal value
changes.

---

# Date-only History Editing

NarrativeLine stores Event date information in:

```text
extensions.history.time
```

The current editor supports three contiguous Civil Time fields:

- `year`
- `month`
- `day`

Precision may stop after any recorded field. `month` requires `year`, and `day`
requires both `year` and `month`. Clearing a coarser field also clears the finer
fields that depend on it.

Unknown finer fields are omitted. A date-only value is not interpreted as
midnight, and NarrativeLine does not create hour, Time Zone, offset, or derived
UTC values merely to support application APIs.

The `year` field uses astronomical year numbering and accepts zero and negative
integers. Month lengths and leap years are validated using the proleptic
Gregorian calendar.

An Event without a recorded date omits the Time Object unless another valid
History field, such as `temporalOrder`, requires it. NarrativeLine does not write
an empty `time` object.

# Entity Association

An Event may reference zero or more Entities.

Opening Entity Picker from Event Detail uses the `Save and Add Related Entity`
action. It validates and saves the Event's current name, description, and
date-only History value before navigation. Returning from Entity Picker does
not undo those saved Event edits, and it does not create an Entity or Relation.

When an Entity is associated with an Event:

- the Entity is linked to the Event
- the required Relation is created automatically

If the Entity already exists, it is reused.

Creating a new Entity uses the separate Entity Create screen opened from Entity
Picker. The Entity is added to the dataset before the Relation is generated.

Entity names are not identifiers. Multiple Entities may have the same name,
and NarrativeLine does not merge Entities automatically based on name equality.

Relations generated by NarrativeLine use the Event as `sourceId` and the
Entity as `targetId`. NarrativeLine does not infer semantic meaning from this
direction.

If a direct Relation already connects the Event and Entity in either direction,
NarrativeLine does not generate another Relation. Multiple existing Relations
between the same objects are preserved, including Relations imported from other
applications.

Users may remove an Entity association from Event Detail. After confirmation,
NarrativeLine removes every direct Relation between that Event and Entity in
either direction. The Entity itself and Relations to other Objects remain.

The user does not otherwise edit Relations directly in the MVP.

---

# Event Deletion

Deleting an Event requires a confirmation in Event Detail. The confirmation
states that the Event, its connected Relations, and any local unsaved edits will
be discarded. Canceling the confirmation leaves the Dataset unchanged.

Confirming deletion removes:

- the Event
- Relations connected to the Event

Associated Entities remain unless explicitly removed.

---

# Timeline Ordering

Timeline ordering is determined using:

1. Valid recorded dates before Events without a recorded date
2. Stored Civil Time year, month, and day values
3. Temporal precision, with coarser precision first for an equal prefix
4. `temporalOrder` when recorded date fields cannot distinguish Events
5. Event ID

Timeline View sorts a derived copy and does not reorder the Dataset's Event
collection. NarrativeLine does not generate `temporalOrder` merely to preserve
presentation order.

---

# Dataset Loading

Loading a dataset performs the following steps:

1. Parse JSON.
2. Validate the Core structure.
3. Validate supported Extensions.
4. Preserve unsupported Extensions whenever possible.
5. Build the internal editing model.

Datasets remain editable even if unsupported Extensions are present.

---

# Dataset Export

Exporting a Dataset performs the following steps:

1. Validate the in-memory dataset.
2. Preserve recorded `temporalOrder` values without regenerating presentation order.
3. Preserve unsupported Extensions whenever possible.
4. Serialize the dataset as JSON.

Exporting does not modify the in-memory Dataset.

Formatting differences that are unrelated to editing should be minimized whenever practical.

---

# Extension Handling

NarrativeLine supports:

- E2R Core
- History Extension

Unsupported Extensions:

- remain attached to their original objects whenever possible
- are not interpreted
- are not modified intentionally

NarrativeLine edits only the Extensions it understands.

---

# Validation

The application validates:

- required Core fields
- the required `version`, `entities`, `events`, and `relations` field types
- non-empty identifier uniqueness across Entities, Events, and Relations
- Relation `sourceId` and `targetId` presence, type, and resolution to an
  Entity or Event in the same Dataset
- that Relations do not use another Relation as an endpoint
- supported History Extension fields
- contiguous History date precision
- Gregorian month and leap-year validity

Validation failures should not automatically discard user data.

Errors should be reported without unnecessary data loss.

Core validation reports stable error codes and JSON Pointer paths. It ignores
unknown Core fields and unknown Extensions; validation of supported Extensions
is separate from Core validation.

---

# Internal Consistency

The application is responsible for maintaining a consistent dataset.

Examples include:

- removing orphaned Relations
- generating required Relations
- maintaining valid Event references
- maintaining timeline ordering

Applications may generate derived values internally, but these values must not become independent sources of truth.

# Future Editing Capabilities

Future versions may introduce:

- Undo / Redo
- Batch editing
- Relative Time editing
- Entity-to-Entity Relation editing
- Automatic merge support
- Conflict resolution
- Incremental validation
- Extension plug-in support
